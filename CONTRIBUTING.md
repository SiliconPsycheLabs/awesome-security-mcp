# Contributing to Awesome Security MCP

Thanks for considering a contribution! This list is curated for accuracy and usefulness, not length.

## Ground rules

1. **One MCP server per PR** (or a small, coherent batch) with a clear reason it belongs.
2. **Format:** `- [Name](URL) - One-line factual description (not marketing copy).`
   Optional status prefixes: `:star:` (mature/widely used), `:new:` (promising newer project), `:package:` (notable toolkit), `:zzz:` (inactive/reference). No icon means no special maturity designation.
3. **Verify the link works** and, for active entries, that the project is maintained (recent commits/releases or a living service). Useful historical/reference entries are allowed when clearly marked `:zzz:` with their lifecycle status.
4. **Disclose hosted status and proprietary/source-available licensing** where relevant (e.g. SONAR Source-Available License).
5. **No duplicates** — search the list before adding.
6. **Alphabetical order** within each section.
7. **Honest descriptions** — what the tool actually does, not what its landing page promises.
8. **No self-promotion without disclosure** — if it's your own project, say so in the PR.

## Emoji conventions

- :star: widely-used, mature project
- :new: promising newer project (less than ~1 year old)
- :package: notable package/toolkit
- :zzz: inactive or unmaintained (kept for reference only)

## Process

1. Fork the repo and create a branch (`add-<tool-name>`).
2. Edit `README.md` following the rules above. Only MCP-related entries: MCP servers, clients/hosts, transports, best practices and learning resources.
3. Open a PR with a short justification and any relevant links (docs, release notes).
4. A reviewer will check the link, description accuracy, and section fit before merging.

## Reporting issues

Found a dead link, a stale description, or a tool that no longer belongs? Open an issue with the section and the reason.
